Kubernetes: обновление, масштабирование и откат Deployment

Как выкатить новую версию, посмотреть историю и быстро откатиться

Как работает обновление

Deployment по умолчанию использует стратегию RollingUpdate: новые поды поднимаются постепенно, а старые удаляются только после того, как новые стали готовы. Поэтому readiness probe имеет прямое значение: без неё Kubernetes не знает, когда новый под можно считать рабочим.

Две настройки управляют темпом обновления:

  • maxSurge — сколько подов можно создать сверх желаемого количества;
  • maxUnavailable — сколько подов может быть недоступно во время обновления.
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 0

Значение maxUnavailable: 0 означает, что сервис не теряет мощность во время выкатки.

Пошаговый сценарий выкатки

  • Проверьте текущее состояние: kubectl get deployment <name> -n <ns>.
  • Посмотрите, что изменится: kubectl diff -f deployment.yaml.
  • Примените изменения: kubectl apply -f deployment.yaml или обновите образ через set image.
  • Дождитесь результата: kubectl rollout status deployment/<name>.
  • Если выкатка зависла, проверьте новые поды: kubectl get pods -n <ns> и kubectl describe pod <pod>.
  • При проблеме откатитесь: kubectl rollout undo deployment/<name>.

Типичные проблемы

СимптомВероятная причинаЧто сделать
ProgressDeadlineExceeded в статусеНовые поды не становятся Ready в отведённое времяПроверить readiness probe и логи нового пода, затем откатить
Старые поды не удаляютсяНовые не проходят readiness, а maxUnavailable равен 0Исправить приложение или временно откатить
После отката приложение всё равно работает со старой конфигурациейИзменился ConfigMap или Secret, а поды не перезапускалисьkubectl rollout restart deployment/<name>
Нет подходящей ревизии для откатаРевизии очищены по revisionHistoryLimitЗадать разумное значение этого параметра (например, 10) и хранить манифесты в git
Храните манифесты Deployment в git. История ревизий Kubernetes показывает, что менялось на уровне образа и шаблона пода, но не заменяет систему контроля версий для самих манифестов.

Рекомендации

  • Всегда задавайте readiness probe, иначе Kubernetes не сможет корректно оценить готовность новых подов.
  • Не используйте тег latest: откат и воспроизводимость ломаются, когда образ меняется под одним именем.
  • Для критичных сервисов ставьте maxUnavailable: 0 и проверяйте rollout status в CI/CD.
  • Выставляйте revisionHistoryLimit, чтобы не копить сотни старых ReplicaSet.
