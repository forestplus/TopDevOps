HTTP, HTTPS и веб-коммуникация

HTTP — протокол прикладного уровня для связи клиента и сервера. Работает по модели «запрос → ответ» и является stateless.

HTTPS добавляет шифрование SSL/TLS. Порт 443 (у HTTP — 80). Защищает от перехвата и подмены данных.

Важные заголовки

  • Host — доменное имя сервера
  • Content-Type — тип данных (application/json)
  • Authorization — токен аутентификации
  • Accept — ожидаемый формат ответа
  • Cookie — данные сессии
  • Cache-Control — инструкции кеширования

Stateless vs Stateful

HTTP не запоминает состояние между запросами. Для «памяти» используют cookies, сессии или JWT токены.

REST API и веб-сервисы

API — набор правил для общения программ. REST — архитектурный стиль построения таких интерфейсов: stateless, resource-based URLs, стандартные HTTP методы, JSON формат.

6 принципов REST

  1. Client-Server — разделение ответственности
  2. Statelessness — нет состояния между запросами
  3. Cacheability — ответы можно кешировать
  4. Uniform Interface — единый интерфейс
  5. Layered System — многослойность
  6. Code on Demand (опционально)

Нормализация

  • 1NF — атомарные значения, нет повторяющихся групп
  • 2NF — 1NF + нет частичной зависимости от составного ключа
  • 3NF — 2NF + нет транзитивных зависимостей
  • BCNF — усиленная 3NF: каждый детерминант — кандидатный ключ

ACID свойства транзакций

A — Atomicity

Всё или ничего. Либо все операции выполнены, либо ни одной.

C — Consistency

Данные всегда переходят из одного валидного состояния в другое.

I — Isolation

Параллельные транзакции не влияют друг на друга.

D — Durability

После COMMIT изменения сохранятся даже при аварии.

Мониторинг, логирование и Observability

Observability — способность понять внутреннее состояние системы по её внешним выходным сигналам. Три столпа: метрики, логи, трейсы.

Три столпа Observability

Metrics (Метрики)

Числовые данные во времени: CPU usage, memory, request rate, latency, error count. Агрегируются, дешёвые в хранении.

Logs (Логи)

Текстовые события с timestamp: ошибки, warnings, debug info. Детализированные, дорогие в объёме.

Traces (Трейсы)

Сквозная трассировка запроса через микросервисы. Показывают где bottleneck, как распределена задержка.

Prometheus + Grafana

Prometheus — time-series database для сбора и хранения метрик. Pull-модель: сам ходит по endpoints /metrics. Grafana — визуализация дашбордов поверх Prometheus/Loki/Elasticsearch.

ELK Stack (Elasticsearch, Logstash, Kibana)

Популярный стек для централизованного логирования:

  • Elasticsearch — search & analytics engine (хранит индексы логов)
  • Logstash — pipeline обработки (parse, enrich, transform)

Logging best practices

  • Structured logging — JSON format вместо plain text (легче парсить)
  • Correlation ID — уникальный ID на весь жизненный цикл запроса
  • Levels discipline — DEBUG/INFO/WARN/ERROR/FATAL осмысленно
  • No PII in logs — маскировать passwords, tokens, personal data
  • Centralized collection — все логи в одно место (Loki/ELK/CloudWatch)
  • Retention policy — defined TTL для разных уровней (debug короче, audit дольше)

Сценарные задачи и System Design

Типовые задачи проектирования систем и ключевые моменты для каждой:

URL Shortener (bit.ly)

  • Генерация уникального короткого кода (base62 encoding)
  • Хранение映射 long URL → short code (KV store: Redis/DynamoDB)
  • Redirect через 301/302
  • Analytics: клики, география (async via Kafka)
  • Кеширование горячих URL в Redis

Chat Application (WhatsApp)

  • WebSocket для realtime доставки
  • Message queue (Kafka) для offline delivery
  • Storage: per-user inbox model vs write-fanout
  • Read receipts, typing indicators
  • End-to-end encryption
  • Presence service (online/offline tracking)

E-commerce Backend (Amazon)

  • Catalog service (search via Elasticsearch)
  • Cart & checkout (distributed transactions / saga pattern)
  • Inventory management (optimistic locking)
  • Payment integration (idempotency keys)
  • Order processing pipeline (event-driven)
  • Recommendation engine (ML + caching)

Notification System

  • Multi-channel: Email, SMS, Push, In-app
  • Template rendering service
  • Priority queues (urgent > normal)
  • Retry with exponential backoff
  • Rate limiting per user/channel
  • Delivery tracking and analytics

Rate Limiter

  • Algorithms: Token Bucket, Leaky Bucket, Sliding Window
  • Implementation: Redis INCR + EXPIRE
  • Per-user / per-IP / per-API-key limits
  • Distributed rate limiting (shared Redis cluster)
  • Graceful degradation: 429 Too Many Requests + Retry-After header

Вопросы и ответы

Ниже собраны вопросы из всех разделов с краткими ответами.

Основы Backend

Что такое backend разработка?

Ответ: Серверная часть приложения, отвечающая за бизнес-логику, работу с БД, аутентификацию и API.

Пользователь не видит бэкенд напрямую, но именно он обеспечивает всю функциональность.

Чем отличается frontend от backend?

Ответ:

  • Frontend — клиентская часть (браузер), отвечает за UI/UX, использует HTML/CSS/JS.
  • Backend — серверная часть, отвечает за логику, данные, безопасность, использует Java/Python/Node.js.
Что происходит при вводе URL в браузере?

Ответ:

  1. DNS-запрос для получения IP-адреса
  2. Установка TCP соединения
  3. Отправка HTTP-запроса на сервер
  4. Сервер обрабатывает запрос (бизнес-логика + обращение к БД)
  5. Возврат HTTP-ответа (HTML/JSON)
  6. Браузер рендерит страницу
Каковы обязанности backend разработчика?

Ответ:

  • Проектирование серверной логики
  • Создание и поддержка REST API
  • Работа с базами данных (SQL/NoSQL)
  • Реализация аутентификации и авторизации
  • Настройка серверов и деплой
  • Обеспечение безопасности приложения
  • Оптимизация производительности и масштабируемости
  • Работа с инструментами DevOps и облачными платформами

HTTP и HTTPS

Разница между HTTP и HTTPS?

Ответ: HTTPS = HTTP + TLS/SSL шифрование.

  • HTTP передаёт данные открытым текстом (порт 80)
  • HTTPS шифрует весь трафик (порт 443), защищая от перехвата и подмены
В чём разница между PUT и PATCH?

Ответ:

  • PUT заменяет ресурс целиком (идемпотентен)
  • PATCH обновляет только указанные поля

Пример: PUT меняет весь объект User, PATCH меняет только email.

Что такое stateless протокол?

Ответ: Сервер не хранит информацию о предыдущих запросах клиента. Каждый запрос должен содержать всю необходимую информацию самостоятельно.

Для поддержания «памяти» используются cookies, sessions или JWT токены.

Назовите принципы REST.

Ответ:

  1. Client-Server
  2. Statelessness

REST vs SOAP — когда что использовать?

Ответ:

Java

Разница между интерфейсом и абстрактным классом?

Ответ:

  • Интерфейс — чистый контракт (до Java 8 только abstract методы), поддерживает multiple inheritance. Определяет «что делать».
  • Абстрактный класс — может иметь concrete методы, поля, конструкторы, но single inheritance. Предоставляет «общую основу».
ArrayList vs LinkedList?

Ответ:

  • ArrayList — динамический массив: O(1) random access, O(n) insert/delete в середине
  • LinkedList — двусвязный список: O(n) access, O(1) insert/delete на краях

Для большинства случаев ArrayList быстрее из-за locality of reference.

HashMap vs HashSet?

Ответ:

  • HashMap хранит пары key→value
  • HashSet хранит только уникальные элементы (внутренне использует HashMap с dummy value)

Оба обеспечивают O(1) средний поиск.

Spring Framework

Что такое Dependency Injection и типы DI?

Ответ: Техника передачи зависимостей объекту извне вместо самостоятельного создания.

Типы:

  1. Constructor injection (рекомендуется — неизменяемость, обязательность)
  2. Setter injection (для опциональных зависимостей)
  3. Field injection (@Autowired — проще, но хуже тестируемость)
Разница между @Component, @Service и @Repository?

Ответ: Все три являются стереотипами @Component.

  • @Service маркирует бизнес-слой
  • @Repository — DAO слой (добавляет translation of persistence exceptions)

Функционально одинаковы, семантически различаются для читаемости и AOP.

Как Spring Boot стартует приложение?

Ответ: Последовательность запуска:

  1. main() вызывается
  2. SpringApplication.run()
  3. Автоконфигурация (читает META-INF/spring.factories)
  4. Создание ApplicationContext
  5. Сканирование @Component/@Configuration
  6. Регистрация бинов
  7. Старт embedded server (Tomcat/Jetty/Netty)
  8. Приложение готово

REST на Spring Boot

Зачем нужны DTO?

Ответ: DTO отделяют внешнюю форму данных от внутренней модели. Позволяют:

  • Скрыть чувствительные поля (password)
  • Контролировать сериализацию
  • Избежать lazy loading проблем
  • Валидировать вход отдельно от entity
Как глобально обрабатывать исключения?

Ответ: Через @RestControllerAdvice + @ExceptionHandler.

Один класс перехватывает все исключения и возвращает единообразный error response с нужным HTTP статусом и сообщением.

Базы данных

Объясните 1NF, 2NF, 3NF.

Ответ:

  • 1NF: атомарные значения, нет повторяющихся групп
  • 2NF: 1NF + каждый неключевой атрибут полностью зависит от всего первичного ключа (нет partial dependency)
  • 3NF: 2NF + нет transitive dependency (неключевые атрибуты не зависят друг от друга)
Когда создавать индекс?

Ответ: Когда столбец часто используется в WHERE, JOIN, ORDER BY.

Индекс ускоряет чтение, но замедляет запись (INSERT/UPDATE/DELETE). Не индексируйте низкокардинальные столбцы (пол, boolean).

Что такое ACID?

Ответ: Свойства транзакций:

  • Atomicity — вся транзакция или ничего
  • Consistency — данные всегда в валидном состоянии
  • Isolation — параллельные транзакции не мешают друг другу
  • Durability — после commit данные переживают crash

Hibernate и JPA

Что такое проблема N+1 и как решить?

Ответ: Загружаем список из N сущностей, каждая имеет lazy связь → Hibernate делает 1 запрос на список + N запросов на связи.

Решения:

  • JOIN FETCH в JPQL
  • @EntityGraph
  • Batch fetching
  • EAGER fetch (осторожно!)
EAGER vs LAZY loading?

Ответ:

  • EAGER — связанные данные грузятся сразу вместе с родителем
  • LAZY — грузятся при первом обращении к getter

По умолчанию: @ManyToOne/@OneToOne = EAGER, @OneToMany/@ManyToMany = LAZY. Рекомендуется LAZY + явный fetch когда нужно.

Безопасность

Как работает JWT?

Ответ: JWT состоит из трёх base64url частей:

  1. Header — алгоритм подписи
  2. Payload — claims (userId, role, exp)
  3. Signature — подпись секретом

Сервер проверяет подпись при каждом запросе. Токен самодостаточен — сервер не хранит сессии.

Как защититься от SQL Injection?

Ответ:

  • Никогда не конкатенировать пользовательский ввод в SQL
  • Использовать PreparedStatement / параметризованные запросы
  • В JPA/Hibernate это сделано автоматически через JPQL/Criteria API
  • Input validation, least privilege DB accounts
Session-based vs Token-based authentication?

Ответ:

  • Session: сервер хранит состояние, клиент получает session ID в cookie. Масштабирование сложнее (sticky sessions).
  • Token (JWT): сервер ничего не хранит, токен содержит все claims. Лучше для микросервисов и SPA, но logout требует blacklist или короткого TTL.

Архитектура

Монолит vs микросервисы — плюсы и минусы?

Ответ:

Монолит:

  • ✅ Прост в разработке/деплое, одна кодовая база, легко дебажить
  • ❌ Сложно масштабировать части независимо, technology lock-in

Микросервисы:

  • ✅ Независимый деплой, tech diversity, fault isolation
  • ❌ Distributed complexity, network overhead, data consistency challenges
Vertical vs Horizontal scaling?

Ответ:

  • Vertical (scale up): добавить CPU/RAM одному серверу. Просто, но есть предел и single point of failure.
  • Horizontal (scale out): добавить больше серверов за load balancer. Практически бесконечно масштабируемо, но сложнее в управлении.

Кеширование

Стратегии кеширования?

Ответ:

  • Cache-aside (lazy loading): приложение проверяет кеш → miss → fetch DB → store cache
  • Write-through: пишет и в кеш и в DB одновременно
  • Write-behind: пишет в кеш, DB обновляется асинхронно
  • Read-through: кеш-слой сам загружает из DB
Redis vs Memcached?

Ответ:

  • Redis: богатые структуры данных (lists, sets, hashes, sorted sets), persistence (RDB/AOF), replication, pub/sub, transactions
  • Memcached: только simple key-value, нет persistence, но чуть быстрее для простых кейсов

Redis универсальнее.

Асинхронная обработка

Kafka vs RabbitMQ — когда что?

Ответ:

  • Kafka: high-throughput event streaming, retention истории, replay, log aggregation, real-time analytics
  • RabbitMQ: traditional task queues, complex routing (exchanges/bindings), lower throughput but richer delivery semantics, simpler setup
Что такое Dead Letter Queue (DLQ)?

Ответ: Специальная очередь для сообщений, которые не удалось обработать после N retry.

Предотвращает бесконечные циклы повторной обработки. Сообщения в DLQ анализируются вручную или автоматически для диагностики.

DevOps и деплой

Контейнер vs виртуальная машина?

Ответ:

  • VM эмулирует целое железо + guest OS (тяжёлая, минуты старта)
  • Контейнер разделяет host kernel, изолирует только process space (лёгкий, секунды старта)

Docker container ≈ процесс с своей файловой системой и networking.

Blue-green deployment vs rolling update?

Ответ:

  • Blue-green: две идентичные среды, traffic переключается atomically с blue на green. Instant rollback. Дороже (2x ресурсы).
  • Rolling update: постепенно заменяет старые pod'ы новыми (K8s default). Дешевле, но slower rollback.
Основные компоненты control plane Kubernetes?

Ответ:

  • kube-apiserver — единственная точка входа
  • etcd — распределённое KV хранилище состояния
  • kube-scheduler — выбирает node для пода
  • kube-controller-manager — контроллеры (deployment, replica, endpoint и др.)
  • cloud-controller-manager — интеграция с cloud provider

Monitoring & Observability

Что такое RED methodology?

Ответ: Подход к мониторингу микросервисов:

  • Rate — количество запросов в секунду
  • Errors — доля ошибочных ответов
  • Duration — время обработки (percentiles p50/p95/p99)

Эти три метрики дают быстрый взгляд на здоровье сервиса.

Чем отличаются liveness, readiness и startup probes?

Ответ:

  • livenessProbe — если fail, kubelet перезапускает контейнер (deadlock/hang detection)
  • readinessProbe — если fail, pod убирается из Service endpoints (ещё не готов обслуживать)
  • startupProbe — временно отключает остальные probes пока приложение медленно инициализируется (>60s)
Зачем нужен correlation ID в логах?

Ответ: Уникальный идентификатор, присваиваемый каждому запросу на входе и пробрасываемый через все микросервисы.

Позволяет собрать всю цепочку событий одного запроса в ELK/Loki несмотря на распределённую природу системы.

Prometheus pull vs push модель?

Ответ:

  • Pull (default): Prometheus сам ходит по targets каждые N секунд. Лучше для долгоживущих сервисов,自动 discovery.
  • Push (via Pushgateway): приложение само отправляет метрики. Нужно для ephemeral jobs (batch/cron), которые живут меньше scrape interval.
Что такое OpenTelemetry?

Ответ: Vendor-neutral стандарт CNCF для instrumentation applications.

  • Единый API/SDK для generation of traces, metrics, logs
  • Collector component для processing/exporting telemetry
  • Поддержка многих backend'ов (Jaeger, Zipkin, Prometheus, OTLP)

Появился как merge Opencensus + OpenTracing.
