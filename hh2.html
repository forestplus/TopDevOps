1. Kubernetes / OpenShift / OKD

В чём главная сложность миграции с OKD 3.11 на OKD 4.x? Можно ли сделать in-place upgrade?
Прямой in-place upgrade с 3.11 на 4.x официально не поддерживается и крайне рискован. Это не просто обновление версии, а смена парадигмы:
  • ОС: Переход с классического RHEL/CentOS на immutable Fedora CoreOS.
  • Рантайм: Замена Docker на CRI-O.
  • Управление: Вместо Ansible-скриптов используется декларативное управление через Machine Config Operator (MCO) и Operator Framework.
«Я бы не стал делать in-place upgrade. Стратегия — side-by-side: поднимаем новый кластер OKD 4.x параллельно, настраиваем GitOps-доставку, и поэтапно (волнами) мигрируем сервисы с 3.11 на 4.x, начиная с тестовых сред. Это минимизирует риск падения production».
Как обеспечить безопасность в OKD при миграции приложений?
В OKD 4.x ужесточены политики безопасности. Нужно проверить:
  • SCC (Security Context Constraints): Заменить использование anyuid на запуск от непривилегированного пользователя или использовать restricted-v2.
  • Pod Security Admission: Убедиться, что манифесты соответствуют стандартам (не требуют root, не монтируют чувствительные hostPath).
  • Image Pull Secrets: Перенести их в новый кластер или настроить интеграцию с внутренним registry.
Как работает обновление нод в OKD 4.x?
Через Machine Config Operator (MCO). Вы вносите изменения в MachineConfig (например, настройка ядра, systemd-юниты, сертификаты). MCO применяет изменения к нодам одного пула (pool) по очереди: cordons ноду, drain'ит поды, применяет конфигурацию, перезагружает ноду (если требуется), uncordons. Это обеспечивает zero-downtime обновление инфраструктуры, если приложения правильно настроены на graceful shutdown и имеют pod disruption budgets (PDB).

2. CI/CD (GitLab)

Как вы будете стандартизировать CI/CD для 60+ сервисов?
Через создание централизованных шаблонов (include: remote в GitLab CI).
  • Создаём базовые шаблоны для сборки (build), тестирования (test), сканирования безопасности (SAST/DAST) и деплоя (deploy).
  • Разработчики подключают один файл .gitlab-ci.yml, который наследует логику.
  • Внедряем pipeline as code и версионирование Helm-чартов.
  • Настраиваем правила (rules) для автоматического запуска только при изменении соответствующих путей.
«Цель — дать разработчикам "золотой путь" (Golden Path). Они не должны думать о том, как написать пайплайн, они просто подключают стандартный шаблон, который уже содержит best practices по безопасности и деплою».
Как реализовать безопасный деплой в production через GitLab CI?
  • Использование environments с ручным подтверждением (when: manual) для production.
  • Настройка protected branches и protected tags.
  • Интеграция с чатом (Slack/Telegram) для нотификации о статусе и запроса аппрува.
  • Стратегия деплоя: Rolling Update с настроенными readinessProbe и livenessProbe, либо Canary для критичных сервисов.
  • Автоматический rollback при провале health-checks после деплоя.

3. High Availability и Active-Active (2 ЦОД)

Как вы спроектируете архитектуру Active-Active для stateful-приложений (БД, Kafka) между двумя ЦОД?
Настоящий Active-Active для stateful-сервисов сложен из-за задержек сети (latency) и риска split-brain.
  • Kubernetes: Два независимых кластера (по одному в каждом ЦОД), управляемых через GitOps (ArgoCD/Flux). Растягивать один кластер на 2 ЦОД (stretched cluster) не рекомендую из-за требований к кворуму etcd и задержкам.
  • Базы данных (PostgreSQL): Синхронная репликация возможна только при очень низкой задержке (< 1-2 мс). Чаще используется асинхронная репликация (с риском потери части данных при failover) или решения типа Patroni с автоматическим failover, но с ручным или полуавтоматическим переключением трафика.
  • Kafka: Использование MirrorMaker 2 или Cluster Linking для асинхронной репликации топиков между ЦОД.
  • Трафик: Глобальная балансировка (GSLB / DNS с низким TTL) или Anycast для распределения запросов.
«Я бы начал с аудита RPO и RTO. Если бизнес допускает RPO > 0, мы используем асинхронную репликацию. Если RPO = 0, требуется синхронная репликация, что накладывает жёсткие ограничения на расстояние между ЦОД (latency). Часто оптимальным компромиссом является Active-Passive для состояния и Active-Active для stateless-сервисов».
Как избежать split-brain при failover между ЦОД?
  • Использование механизмов fencing (например, STONITH для серверов или блокировка на уровне хранилища).
  • Для Kubernetes: использование решений, которые не полагаются на кворум etcd, растянутый между ЦОД. Лучше иметь два независимых кворума.
  • Чёткие runbooks и автоматизированные сценарии переключения, которые гарантируют, что старый primary полностью остановлен перед поднятием нового.

4. Apache Kafka (3.x → 4.x, KRaft)

В чём суть перехода на Kafka 4.x и как вы его спланируете?
Главное изменение: полное удаление ZooKeeper и переход на KRaft (Kafka Raft metadata mode) как единственный способ хранения метаданных. План миграции:
  1. Аудит: Проверка версий клиентских библиотек (producer/consumer), Kafka Connect, Schema Registry. Устаревшие клиенты могут не поддерживать новые API.
  2. Подготовка: Обновление кластера до последней версии 3.x с включением режима KRaft в dual-stack (ZooKeeper + KRaft одновременно).
  3. Миграция метаданных: Перенос метаданных из ZK в KRaft-кворум.
  4. Отключение ZK: Вывод ZooKeeper из эксплуатации.
  5. Обновление: Rolling upgrade брокеров до версии 4.x.
  6. Мониторинг: Адаптация дашбордов и алертов (старые ZK-экспортеры больше не работают, нужны метрики из JMX/Kafka API).
«Это не просто "yum update". Это смена нервной системы кластера. Ключевой риск — совместимость клиентов и инструментов мониторинга. Поэтому обязателен полноценный PoC на стенде, имитирующем production-нагрузку».
Как обеспечить репликацию Kafka между двумя ЦОД в модели Active-Active?
С помощью MirrorMaker 2 (или нативного Cluster Linking в новых версиях). Важно настроить:
  • Асинхронную репликацию топиков.
  • Смещение оффсетов (offset translation), чтобы при failover консьюмеры в резервном ЦОД могли продолжить чтение с правильного места.
  • Защиту от циклической репликации (replication loops), если топик уже существует в целевом кластере.

5. Управление секретами (Vault)

Как интегрировать Vault с Kubernetes/OKD для безопасной выдачи секретов?
Лучшая практика — использование Vault Agent Injector или внешнего секретного оператора (например, External Secrets Operator).
  • Приложение не знает о Vault. Оно читает секреты из файлов или переменных окружения.
  • Vault Agent аутентифицируется в Vault через Kubernetes Auth Method (используя ServiceAccount token пода).
  • Vault проверяет роль и политику, и выдаёт динамический или статический секрет.
  • Agent автоматически обновляет (renew/rotate) секреты и перезапускает приложение при необходимости.
«Секреты никогда не должны храниться в Git или передаваться через переменные окружения GitLab CI в открытом виде. Vault должен быть единственным источником истины, а доступ к нему — строго через аутентификацию по идентичности сервиса (ServiceAccount)».
Как обеспечить High Availability и Disaster Recovery для самого Vault?
  • HA: Запуск нескольких нод Vault с использованием хранилища с поддержкой HA (например, Raft storage или Consul). Настройка auto-unseal (через AWS KMS, GCP KMS или HashiCorp HSM), чтобы не вводить ключи вручную при перезагрузке.
  • DR: Настройка DR Replication (асинхронная репликация на резервный кластер Vault в другом ЦОД). В случае катастрофы основной кластер промоутится из DR-реплики.

6. Observability (VictoriaMetrics, Grafana, Elastic)

Почему в стеке указана VictoriaMetrics, а не классический Prometheus?
VictoriaMetrics полностью совместима с Prometheus API, но решает его проблемы масштабирования:
  • Значительно меньшее потребление RAM и CPU.
  • Высокая скорость ingest (записи) и query (чтения).
  • Простота эксплуатации: один бинарный файл (vm-single) или кластерное решение (vm-cluster) без сложных зависимостей.
  • Долгосрочное хранение (long-term retention) без необходимости использовать Thanos или Cortex.
Как вы выстраиваете процесс алертинга, чтобы команда не страдала от "alert fatigue"?
  • Разделение алертов на Page (требуют немедленного действия, влияют на SLO) и Ticket (можно исправить в рабочее время).
  • Использование SLO и Error Budgets. Алертим не на высокую загрузку CPU саму по себе, а на симптомы, влияющие на пользователя (высокая задержка, рост ошибок).
  • Группировка алертов в Alertmanager (по кластеру, сервису), чтобы при падении ноды не прилетало 100 писем, а одно агрегированное.
  • Регулярный пересмотр и отключение бесполезных алертов (настройка "alert hygiene").
«Хороший алерт должен отвечать на три вопроса: что случилось, насколько это критично и что делать прямо сейчас (ссылка на runbook)».

7. IaC и Ansible

Как вы организуете управление конфигурациями с помощью Ansible в крупной инфраструктуре?
  • Использование Ansible Collections для переиспользования ролей.
  • Чёткая структура инвентаря: группировка по окружениям (dev, stage, prod) и ролям.
  • Шифрование чувствительных данных через Ansible Vault (или, что лучше, передача секретов из внешнего Vault, а не хранение их даже в зашифрованном виде в Git).
  • Идемпотентность: каждый плейбук должен быть безопасен для многократного запуска.
  • CI/CD для Ansible: линтинг (ansible-lint), dry-run перед применением, применение через пайплайн с аппрувом.
В вакансии упомянут Terraform как плюс. Как он вписывается в стек с Ansible и OKD?
Terraform используется для провижининга инфраструктуры (создание ВМ, сетей, балансировщиков, S3-бакетов в облаке или vSphere). Ansible используется для конфигурации этих ВМ (если они не immutable) или для начальной настройки. OKD/Kubernetes управляет жизненным циклом приложений. Важно соблюдать границу: Terraform создаёт ресурсы, Ansible/K8s их настраивает. Состояние Terraform должно храниться в удалённом бэкенде (S3 + DynamoDB для lock) с контролем доступа.

8. SRE и ITSM практики

Как вы совмещаете эксплуатацию (тушение пожаров) и модернизацию (развитие платформы)?
  • Выделение явной ёмкости (capacity) в спринте. Например, 70% на проекты развития (roadmap), 30% на технический долг и инциденты.
  • Если инцидентов становится больше 30%, мы останавливаем новые фичи и проводим Incident Review / Post-mortem, чтобы найти корневую причину и автоматизировать её устранение.
  • Внедрение практик Chaos Engineering (на тестовых средах) и регулярные DR-учения, чтобы находить слабые места до того, как они сломают прод.
«Нельзя бесконечно добавлять фичи, если фундамент трещит по швам. Мой опыт внедрения ITSM/ITIL помогает выстроить процесс Change Management, чтобы модернизация не ломала эксплуатацию, а автоматизация сокращала количество ручных инцидентов».
Что такое Post-mortem и как вы его проводите?
Это анализ инцидента после его устранения. Главные правила:
  • Blameless culture: Мы ищем причину в процессе или системе, а не виноватого человека.
  • Документирование таймлайна: что произошло, когда обнаружили, как реагировали, когда починили.
  • Определение Root Cause (например, методом "5 почему").
  • Создание action items с конкретными владельцами и сроками (например, "добавить алерт на X", "исправить плейбук Y").

9. Архитектура и Лидерство

Как вы принимаете сложные архитектурные решения (например, выбор между Elastic и OpenSearch)?
Я использую структурированный подход:
  1. Сбор требований: что нужно бизнесу и разработке (производительность, стоимость, функционал).
  2. Анализ альтернатив: сравнение 2-3 вариантов по критериям (TCO, сложность поддержки, community support, лицензирование).
  3. PoC (Proof of Concept): Развёртывание пилота на реалистичных данных и нагрузке.
  4. Фиксация решения в ADR (Architecture Decision Record): контекст, рассмотренные варианты, принятое решение и его последствия.
«В случае Elastic vs OpenSearch: если у нас уже есть экспертиза и лицензии, или нужны специфичные фичи Elastic (например, продвинутый ML), выбираем Elastic. Если важна полная open-source независимость и базовый функционал логов — OpenSearch. Решение всегда должно быть обосновано данными из PoC, а не хайпом».
Как вы будете выстраивать работу с командой из 10+ человек и заказчиком?
  • С командой: Прозрачный бэклог, регулярные 1-on-1, чёткое распределение зон ответственности (platform, SRE, CI/CD), поощрение кросс-функциональности (чтобы не было bus factor = 1).
  • С заказчиком: Говорить на языке бизнеса. Не "мы обновляем Kafka", а "мы снижаем риск простоя торговой площадки и ускоряем обработку транзакций". Регулярные демо результатов и прозрачный roadmap.
  • Смежные команды (DBA, сеть, ИБ): Вовлекать их на этапе проектирования (Shift-Left), а не ставить перед фактом перед деплоем.
